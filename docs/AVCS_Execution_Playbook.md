## 3. THE FIVE EXECUTION PRINCIPLES

Execution is governed by five non-negotiable principles.

### Principle 1 — Single Ownership

Every action has **one accountable owner**.

No committees. No diffusion. No ambiguity.

**Failure Mode:**
Diffused ownership → delay or inaction.

**Diagnostic Questions:**

- Is there a named owner for every critical action?
- Is ownership recorded before action begins?
- Can ownership be transferred without explicit handover?

**Evidence Required:**

- ownership records,
- decision logs,
- handover documentation.

### Principle 2 — Clear Intent

Before action begins, intent must be explicit:

- What must change?
- Why it matters.
- What success looks like.
- What failure costs.

**If intent cannot be stated clearly, execution is postponed.**

**Failure Mode:**
Unclear intent → misaligned execution.

**Diagnostic Questions:**

- Can the operator state what success looks like?
- Is intent documented before action begins?
- Is failure cost explicit?

**Evidence Required:**

- intent statements,
- success criteria,
- failure-cost documentation.

### Principle 3 — Minimal Interfaces

Execution systems must reduce friction:

- fewer handovers,
- fewer approvals,
- fewer interpretations.

Complex execution paths indicate poor design.

**Failure Mode:**
Excess interfaces → delay, distortion.

**Diagnostic Questions:**

- How many approvals are required before action?
- How many handovers exist in the critical path?
- Can the path be shortened without loss of control?

**Evidence Required:**

- process maps,
- approval chains,
- handover logs.

### Principle 4 — Reality Feedback Loop

Execution is continuously tested against reality:

- field conditions,
- operational constraints,
- human load,
- safety margins.

**Data that does not affect decisions is removed.**

**Failure Mode:**
Detached execution → false confidence.

**Diagnostic Questions:**

- Is field data used to adjust execution?
- Does the system filter data that does not affect decisions?
- Is there a defined feedback loop from execution to decision?

**Evidence Required:**

- feedback loop documentation,
- field data records,
- adjustment logs.

### Principle 5 — Consequence Awareness

Every executor must understand:

- what breaks if this fails,
- who carries the consequence,
- how fast recovery must occur.

**Execution without consequence awareness is negligence.**

**Failure Mode:**
Low awareness → risk amplification.

**Diagnostic Questions:**

- Does the executor know who carries the consequence?
- Is failure consequence documented?
- Is recovery time defined?

**Evidence Required:**

- consequence documentation,
- role-consequence mapping,
- recovery-time specifications.

## 6. EVIDENCE BEFORE STATUS

Execution does not accept a claimed status — **Authorized, Executing, Verified, Completed** — as evidence of a structural condition.

For every claim, execution requires evidence that existed **at or before the moment** of the act it governs.

For every critical execution state, three things must be independently establishable:

1. The **claimed status** — what the record says.
2. The **required structural condition** — what must actually be true.
3. The **evidence** — what can be independently verified.

If the condition behind the status cannot be shown, the execution state is **not structural**.

**The diagnostic question is:**

> **Show me the condition behind the status.**

This principle is encoded in:

- Charter v1.1, Section 4.3
- CORE v2.1, Law 21
- Code of Ethics v1.1, Section 11
- SIM v1.1, Section 2.3
- INS v1.1, Section 4
- HPSM v1.1, Section 5

## 7. FAILURE HANDLING PROTOCOL

Failure is treated as **information, not drama**.

AVCS requires:

- immediate containment,
- transparent reporting,
- root cause analysis,
- structural correction.

**Blame is irrelevant.**

**Correction is mandatory.**

### 7.1 What Failure Is Not

- Failure is not an event to be hidden.
- Failure is not a person to be blamed.
- Failure is not an excuse to pause correction.

### 7.2 What Failure Is

- Failure is a structural condition.
- Failure is a signal that the architecture is incomplete.
- Failure is a test result.

### 7.3 Failure Handling Sequence

1. **Contain** — stop further degradation.
2. **Report** — document what happened.
3. **Analyze** — identify the structural break.
4. **Correct** — restore structural integrity.
5. **Record** — preserve the pathway.
